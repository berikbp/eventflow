## 2. Project Context

**Название:** EventFlow

**Компания:** MadDevs

**Позиция:** Junior Agentic Developer

**Выбранное тестовое задание:** №9 — «Регистрация на мероприятия».

**Дедлайн:** 2 ноября 2026 года.

### Цель

Создать полноценное веб-приложение для регистрации на мероприятия с ограниченным количеством мест.

Организаторы создают мероприятия, управляют регистрациями, отслеживают количество участников и выполняют check-in.

Пользователи регистрируются по email, получают билеты, могут отменять регистрацию и попадать в лист ожидания, если свободных мест нет.

Система должна поддерживать конкурентные запросы, автоматические уведомления и обновление данных в реальном времени.

Это не просто CRUD-приложение. Основная инженерная ценность проекта — корректность бизнес-логики при конкурентном доступе, надёжная обработка состояний и воспроизводимые тесты.

## 3. Official Assignment Requirements

Следующие требования обязательны. Нельзя пропускать их ради дополнительных возможностей или визуального оформления.

### 3.1. Event Management

Организатор должен иметь возможность:

- Создать мероприятие.
- Указать название и описание.
- Установить дату и время.
- Установить максимальное количество участников.
- Просмотреть список зарегистрированных.
- Просмотреть лист ожидания.
- Изменить дату и время мероприятия.
- Просмотреть статистику регистрации и посещаемости.

### 3.2. Registration

Пользователь должен иметь возможность:

- Открыть страницу мероприятия.
- Зарегистрироваться по email.
- Получить подтверждение и билет.
- Отменить свою регистрацию.
- Узнать свой статус: зарегистрирован или находится в листе ожидания.

Правила:

- Повторная регистрация с тем же email на одно мероприятие не создаёт второго места.
- Количество подтверждённых участников никогда не превышает лимит.
- Все ограничения должны проверяться backend, а не только frontend.

### 3.3. Waiting List

Когда свободных мест нет:

- Новая регистрация попадает в лист ожидания.
- Порядок ожидания определяется моментом регистрации.
- Если подтверждённый участник отказывается, первый пользователь из листа ожидания автоматически получает освободившееся место.
- При продвижении пользователь получает уведомление и билет.
- Очередь должна корректно работать при нескольких одновременных запросах.

### 3.4. Concurrency — Critical Requirement

Один из важнейших сценариев:

На мероприятии осталось ровно одно место.

Два пользователя одновременно отправляют запрос на регистрацию.

Ожидаемый результат:

- Первый успешно зафиксированный запрос получает место.
- Второй пользователь попадает в лист ожидания.
- Количество участников не превышает лимит.
- Никаких потерянных обновлений или дублирующихся регистраций.

Нельзя решать эту проблему обычной проверкой количества мест перед INSERT без защиты от гонок.

Используй надёжные механизмы PostgreSQL: транзакции, блокировки или другие обоснованные средства обеспечения целостности.

Создай автоматические интеграционные тесты конкурентной регистрации на настоящем PostgreSQL.

Дополнительный проверочный сценарий:

20 пользователей одновременно регистрируются на мероприятие вместимостью 5 человек.

Ожидается:
- 5 подтверждённых регистраций.
- 15 записей в листе ожидания.
- Ни одного дубликата.
- Никакого превышения вместимости.

### 3.5. Ticket System

Каждый подтверждённый участник получает билет с уникальным кодом.

Необходимо реализовать:

- Генерацию уникальных кодов.
- Просмотр билета.
- Проверку билета организатором.
- Check-in посредством ввода кода.
- Защиту от повторного check-in.

Один билет может быть использован для входа только один раз.

Повторная попытка check-in должна обрабатываться предсказуемо и не увеличивать счётчик посетителей.

QR-сканер не обязателен. Достаточно формы ввода кода.

### 3.6. Organizer Dashboard

Организатор должен видеть:

- Количество подтверждённых участников.
- Количество людей в листе ожидания.
- Количество прошедших check-in.
- Общую вместимость мероприятия.
- Список участников и их статусы.

Все необходимые счётчики должны обновляться без ручной перезагрузки страницы.

### 3.7. Real-Time Updates

Система должна поддерживать минимум два одновременно открытых клиента.

Например:

- В первом окне пользователь регистрируется.
- Во втором окне организатор видит изменение статистики без обновления.
- После отмены регистрации изменения отображаются у подключённых клиентов.
- После check-in статистика посещаемости обновляется автоматически.

Предпочтительная технология — Server-Sent Events (SSE). WebSocket допустим, если есть техническое обоснование.

Обеспечь корректное получение актуального состояния после переподключения клиента.

### 3.8. Email Notifications

Система должна отправлять логические email-уведомления:

1. Подтверждение регистрации с билетом.
2. Уведомление при автоматическом продвижении из листа ожидания.
3. Напоминание за 24 часа до мероприятия.
4. Уведомление участникам при изменении даты или времени мероприятия.

Обязательные требования:

- Повторная регистрация не создаёт второе подтверждение с новым билетом.
- Напоминание за сутки отправляется ровно один раз каждому соответствующему участнику.
- Отправка уведомлений не должна блокировать HTTP-запросы.
- После перезапуска приложения незавершённые задания не должны теряться.
- Повторная обработка фонового задания не должна создавать дубли логических уведомлений.

Использование настоящего внешнего email-провайдера необязательно.

Предпочтительно использовать локальную SMTP-заглушку, например Mailpit, позволяющую просматривать отправленные письма через браузер.

Для устойчивой обработки уведомлений рассмотри database-backed transactional outbox.

Не заявляй абсолютную гарантию exactly-once доставки внешней почты, если она технически не обеспечена. Разделяй гарантии создания уведомления и фактической доставки.

### 3.9. Event Rescheduling

При переносе мероприятия:

- Новая дата сохраняется в PostgreSQL.
- Подключённые клиенты получают обновлённые данные.
- Зарегистрированные участники получают уведомление.
- Запланированные напоминания пересчитываются.
- Старые задания не должны приводить к некорректным уведомлениям.

Определи и документируй поведение для мероприятия, до которого осталось менее 24 часов.

### 3.10. General Requirements

Официальные общие требования MadDevs:

- Отдельные backend и frontend, взаимодействующие по сети.
- Python, Go или Node.js для backend.
- React или Vue для frontend.
- Реляционная база данных, предпочтительно PostgreSQL.
- Авторизация на усмотрение разработчика, допускается отсутствие входа.
- Использование AI-агента во время разработки ожидается.
- Приложение должно быстро запускаться локально.
- Внешние сервисы разрешается эмулировать.
- Система должна корректно работать в двух вкладках браузера одновременно.
- Данные должны сохраняться после перезапуска приложения.
- Нужно честно описывать реализованные и нереализованные возможности.
- Работоспособность должна подтверждаться воспроизводимыми проверками.

## 5. Architecture Expectations

Предпочтительная архитектура — modular monolith.

Разделяй:

- API routes
- Request/response schemas
- Domain/business logic
- Database models
- Persistence/repositories, где это оправданно
- Background jobs
- Notification handling
- Real-time events

Не помещай всю бизнес-логику в FastAPI endpoints.

Не создавай десятки абстракций без причины.

Спроектируй модель данных с учётом следующих сущностей:

- Event
- Registration
- Ticket
- Notification / Outbox
- Данные организатора или минимальная модель доступа

Отдельная сущность WaitingList необязательна, если она корректно реализуется через статус и порядок Registration.

Продумай:

- Уникальность email внутри мероприятия.
- Нормализацию email.
- Статусы регистраций.
- Уникальность кодов билетов.
- Транзакционное продвижение очереди.
- Конкурентную регистрацию.
- Идемпотентные операции.
- Ограничения базы данных.
- UTC и timezone-aware datetime.
- Безопасность управляющих API.

Выбери максимально простой механизм авторизации, позволяющий безопасно разграничивать действия организатора и участника. Например, локальная учётная запись организатора и непрогнозируемые токены управления регистрацией для участников.

Не усложняй проект полноценной системой ролей и пользователей, если этого не требуют основные сценарии.

## 13. Engineering Principles

Следуй этим правилам:

**1. No blind coding.**

Перед значимыми изменениями изучай существующий код, требования и связанные модули.

**2. No fake completion.**

Не сообщай, что функциональность готова, если остались неработающие основные сценарии.

**3. No unnecessary complexity.**

Не вводи микросервисы, event bus, сложные паттерны и зависимости только ради демонстрации технологий.

**4. Database integrity first.**

Критические ограничения регистрации должны соблюдаться на уровне backend и базы данных.

**5. Security by default.**

Валидация входных данных, безопасные токены, контроль доступа, отсутствие секретов в репозитории.

**6. Test important behavior.**

Особенно конкурентный доступ, повторные запросы и фоновые задания.

**7. Explain important decisions.**

Если есть несколько подходов, кратко сравни их и объясни выбор.

**8. Be transparent.**

Если возникла ошибка или ограничение, укажи это открыто и предложи исправление.

**9. Preserve development evidence.**

Не теряй реальные промпты, проверки, временные метки и принятые решения.

**10. Keep the project runnable.**

После каждого основного этапа проект должен оставаться в запускаемом состоянии.

## 14. How You Should Work With Me

Для каждого крупного этапа используй следующий формат:

### Before implementation
1. Что именно собираемся реализовать.
2. Какие требования закрываем.
3. Какие файлы планируем изменить.
4. Какие риски и edge cases нужно учитывать.
5. Как будем проверять результат.

### During implementation
- Вноси изменения небольшими логическими частями.
- Не переписывай работающий код без необходимости.
- Следи за совместимостью backend и frontend.
- По возможности запускай тесты после значимых изменений.
- Исправляй обнаруженные ошибки.

### After implementation
1. Что реально сделано.
2. Какие файлы изменены.
3. Какие команды выполнены.
4. Какие тесты прошли или не прошли.
5. Какие ошибки обнаружены и исправлены.
6. Какие ограничения остались.
7. Какой следующий логический этап.

Не представляй предполагаемые результаты команд как фактические.

Если твоя среда не позволяет выполнить команду, прямо скажи об этом и покажи, что требуется проверить вручную.
