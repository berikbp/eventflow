# Архитектура

## Реализовано в Foundation

Модульный монолит FastAPI и отдельное React SPA.
Browser → Vite /api proxy → FastAPI → SQLAlchemy AsyncEngine → PostgreSQL.
В Compose приложения обращаются по service DNS; браузер знает только localhost.
Настройки backend читаются из корневого .env или окружения.
Engine создаётся в lifespan и закрывается при shutdown. /health проверяет процесс,
/health/ready выполняет SELECT 1 с лимитом времени и отвечает 503 при сбое БД.
Публичные health ответы не содержат строку подключения.

PostgreSQL хранится в именованном volume. Mailpit доступен для будущего SMTP.
Доменной схемы, workers и маршрутов управления сейчас нет.
Alembic установлен; конфигурация и первая миграция появятся с моделями в Phase 2.

## План следующих этапов (ещё не реализовано)

- Event: дата UTC, вместимость, версия расписания, данные доступа организатора.
- Registration: event_id, нормализованный email, status, последовательный порядок,
  хеш токена управления. UNIQUE(event_id, normalized_email).
- Ticket: уникальный случайный код, registration_id, checked_in_at, отзыв при отмене.
- Outbox: тип, payload, deduplication_key UNIQUE, due_at, попытки, состояние доставки.

API routes → схемы → бизнес-сервисы → SQLAlchemy. Repository вводить только
при повторяющейся логике доступа. Background worker — отдельный процесс того же
backend; PostgreSQL outbox исключает необходимость Redis/Celery.

Любая операция, меняющая занятость/очередь, блокирует Event через SELECT FOR UPDATE
в общей транзакции. Под той же блокировкой проверяются повторная регистрация,
вместимость, отмена, FIFO-продвижение, билет и outbox. Все пути изменения должны
соблюдать один порядок блокировок. Финальные ограничения и тесты — Phase 3.
Порядок FIFO задаётся монотонным ключом при получении блокировки, а не только
timestamp с возможными совпадениями.

SSE передаёт сигнал обновления, клиент получает актуальный snapshot API, включая
после reconnect. В одном backend процессе достаточно простого broadcaster;
при нескольких процессах использовать PostgreSQL LISTEN/NOTIFY как сигнал,
а не как единственное хранилище событий. Это проектное предложение.

Outbox создаётся в той же транзакции, что регистрация/перенос. Worker выбирает
задания с блокировкой, retry/backoff и защитой от устаревшей версии расписания.
UNIQUE ключ гарантирует одно логическое уведомление. SMTP возможен повторно
при crash после отправки до фиксации результата: exactly-once delivery не обещаем.

Предлагаемая политика напоминаний: при создании/переносе менее чем за 24 часа
до начала отправлять одно немедленное напоминание для текущей версии расписания,
если событие ещё не началось; старые версии аннулировать. Уточнить в Phase 5
и покрыть тестами до объявления реализованной.

Организатор: минимальная локальная учётная запись/сессия. Участник: bearer token
управления, хеш в БД; email сам по себе не даёт право отмены. Реализовать до
публикации управляющих API. Не вводить полную систему ролей без необходимости.
